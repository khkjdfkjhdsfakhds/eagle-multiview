### 菜单与快捷键

- **GUI-01（高，仍存在）** macOS 菜单栏只有 Electron 骨架加少量自定义项（与延期的 NF-09 是同一件事）。
  - 原版有十个顶层菜单：应用、资源库、文件、编辑、查找、整理、显示、窗口、插件、帮助。MultiView **完全缺少“资源库”“查找”“整理”“帮助”**，“编辑”和“显示”也只有几项。
  - 原版“编辑”菜单有：重命名、撤销/重做、剪切/复制/粘贴、复制文件路径/文件夹路径/Eagle 链接/缩略图/Base64/名称、创建副本、刷新缩略图、自定义缩略图、全选、文件夹排列、编辑图像、编辑文件夹、从文件夹中移除、丢到回收站。
  - 原版“整理”菜单有：添加标签、添加至文件夹、添加至上次使用的文件夹、评分 0–5、复制/粘贴/清除标签。
  - 原版“显示”菜单有：窗口置顶、各侧栏视图、布局切换、滚动、缩放、打开方式、左右栏开关、显示名称/尺寸/标注、显示子文件夹内容。
  - 窗口菜单的 Minimize / Zoom / Bring All to Front 是英文。当时应用菜单显示的是 npm 包名 `eagle-multiview`；现在 `main.js` 已有 `app.setName(identity.name)`，`package.json` 也有 `productName`，需要确认这一点是否已修复。
  - 建议：在 `main.js` 用模板按原版结构重建菜单，各项通过 IPC 调用渲染进程已有的命令，按选择状态启用或禁用，所有文案用中文。API 不支持的项（以图找图、编辑图像、密码保护、eaglepack）先不放，或灰显。

### 主界面与工具栏

- **GUI-02（中）** 原版窗口工具栏从左到右：后退、前进、文件夹名、缩略图滑块、视图设置、筛选器开关、搜索框。下方还有一条**常驻筛选条**（颜色/标签/文件夹/形状/评分/格式/+）。MultiView 把后退/前进放在每栏里（多栏设计下合理），但没有常驻筛选条。
- **GUI-03（中）** 原版卡片下方的“名称/尺寸/标注”可以通过开关控制；MultiView 固定显示“名称 + 尺寸·大小”，没有开关。
- **GUI-04（中）** 检查器顺序要对照原版：大预览 → 主色圆点 → 名称 → 注释 → 链接（带打开按钮）→ 标签（整行“添加标签”按钮）→ 文件夹（chip + “+”）→ 基本信息（评分/尺寸/大小/格式/添加日期/修改日期）。原版选中文件夹时，检查器显示名称、描述、文件数、占用空间、添加日期、密码保护、“导出文件夹”。
- **GUI-05（低）** 原版侧栏底部有“筛选侧栏项目”输入框；MultiView 没有。
- **GUI-06（低）** 底部状态条“已载入 N / M · X%”和“已同步 HH:MM:SS”是原版没有的元素，百分比含义不明（`src/renderer.js` 的 `#scrollStatus`）。建议改成原版风格的“N 个项目”。
- **GUI-07（低，仍存在）** 术语不一致：侧栏写“全部素材 / 未加标签 / 资料库根目录”，原版是“全部 / 未标签”，库统一叫“资源库”。MultiView 里“资料库”和“资源库”混用（`src/renderer.js` 侧栏、视图标题、toast）。

### 标签管理

- **GUI-08（中）** 原版的标签管理：
  - 左列有“全部 / 未分类 / 常用标签”和标签群组；
  - 右侧按首字母分段，三列 chip 排布，带使用数；
  - 顶栏有网格/列表切换、排序和搜索。

  MultiView 是一长串行列表，每行带“筛选/重命名/合并”文字按钮，没有首字母分段、常用标签、搜索和视图切换。建议按原版结构重做（中文用 `Intl.Collator('zh-Hans-u-co-pinyin')` 取拼音首字母）。“常用标签”如果 API 没有对应字段，就存成 MultiView 本地状态。
- **GUI-09（低）** 同一页有三重标题（面包屑、分栏标题、卡片标题），还有面向开发者的说明文案（“标签颜色仍保存在 MultiView 本地状态”）。
- **GUI-10（低，窄窗）** 分栏宽约 400px 时，“新建分组”按钮会换行；空分组占位行的内边距、字号、背景与正常行不一致；行尾“合并”按钮贴边被裁切。

### 筛选

- **GUI-11（中）** 交互模型不同。原版是常驻筛选条，每个条件一个小弹层，生效后 chip 高亮显示当前值。MultiView 是临时打开的大表单，关闭后看不出哪些条件在生效。建议在每栏标题下加筛选条（窄栏时收成“筛选 (N)”徽标），继续复用 `query-spec`。
- **GUI-12（中）** 缺少的筛选条件：
  - 文件夹、时长、标注、修改日期；
  - 尺寸：原版按宽×高像素，MultiView 只有百万像素；
  - 格式：原版是带计数的勾选列表，MultiView 是自由文本；
  - 标签：原版支持多选、包含任一/全部/排除和“未标签”，MultiView 是文本框。

  AI 类条件（以图找图、语义搜索）API 不支持，标注为限制即可。注意 `/api/v2/item/get` 会忽略范围参数，这些条件都要走客户端过滤管线。
- **GUI-13（低）** 添加日期用的是原生 `<input type=date>`，显示成美式“月/日/年”；“管理标签颜色”放在筛选面板里，位置也不合理。

### 分区 5：主进程与 `lib/` 代码审查（2026-10-13）

范围：`main.js` 全文，`lib/data-hub.js`、`lib/eagle-client.js`、`lib/web-server.js`、`lib/update-service.js`、`lib/export-service.js`、`lib/text-file-service.js`，以及 `src/query-spec.js`。整体质量较高：跨窗口冲突、资料库切换保护、写后回读确认都做得很细。以下是问题：

- **P5-01 ＝ BUG-01 复核（Bug，高，源码确认，待 GUI 验证）** `main.js:1007` 的编辑菜单“撤销”是自定义 `click`，固定发送 `command:undo-delete`；`src/renderer.js:9070` 收到后直接执行 `undoLastTrash()`，不判断焦点。renderer 的 keydown（`src/renderer.js:8737`）只在非输入框时处理 ⌘Z，所以在输入框里按 ⌘Z 时会落到菜单项，文字撤销失效。同一菜单里“重做”仍是 `role: 'redo'`，两者不对称。
  - 方案：菜单项改发 `command:undo`；renderer 判断 `document.activeElement` 是否可编辑，可编辑时执行 `document.execCommand('undo')`，否则执行 `undoLastTrash()`。“重做”同样处理（目前没有删除的重做栈，非编辑状态下可以灰显或不处理）。附带测试：断言菜单模板不再固定发送 undo-delete，并给 renderer 的分派函数写单测。
- **P5-02 ＝ BUG-02 复核（Bug，高，源码确认）** Electron 不支持 `window.prompt()`，调用后直接返回 `null`、不弹窗。以下桌面版入口因此点击后**完全没有反应**：
  - 添加评论（`src/renderer.js:3211`，视频时间点 `:3217`、框选坐标 `:3224` 也在这一流程里）；
  - 编辑评论（`:3255`）；
  - 右键菜单“标签颜色”（`:6165`）；
  - 主进程菜单发来的设置标签颜色（`:9081`）。

  `confirm()` 在 Electron 里可用，删除评论不受影响。
  - 方案：复用现有的应用内模态框（`web-copy-dialog` 或 `feature-ui.js` 的对话框模式）做通用的 `askText()`，替换上面全部 `prompt`。标签颜色改用色板加 `<input type=color>`，与原版色板交互看齐（原版色板细节**待本机核对**）。
- **P5-03（安全，中，源码确认）** Web 访问关闭“需要密钥”后（`#webAccessNoKey`，`lib/web-server.js:219`），服务器监听 `0.0.0.0`，且**不校验 Host 头和 Origin**。这时存在 DNS rebinding 风险：本机或局域网设备访问的任意恶意网页，可以把自己的域名解析到 `127.0.0.1:<端口>`，变成同源后调用 `/rpc`，执行改元数据、合并标签、丢回收站、导出原图等操作。
  - 方案：`handleRequest` 校验 `Host` 只能是 IP 字面量、`localhost` 或 `*.local`；对 POST `/rpc`、`/upload`、`/export/prepare` 额外校验 `Origin`（如果带了）与 Host 一致。改动小，开着密钥时也无副作用。
- **P5-04（Bug／与原版不同，中，推测待验证）** 文件菜单的“新建文件夹”是 `Alt+N`，“新建 TXT”是 `Alt+Shift+N`（`main.js:980-981`），作为全局菜单快捷键注册。macOS 上 ⌥N 是输入 `˜`/`ñ` 的死键，焦点在名称、备注、TXT 编辑器里时，按键可能被菜单截走去新建文件夹。⌘R（重命名，`main.js:1010`）也是全局注册。
  - 原版新建文件夹、重命名的快捷键**待本机核对**。
  - 方案：先在本机验证输入框里按 ⌥N 的表现。若被截走，有两种改法：让菜单项在编辑状态下由 renderer 判断并放行；或改成原版的组合键。
- **P5-05（与原版不同，低，源码确认）** 补充 GUI-01 的菜单细节：
  - “窗口”菜单只有 `minimize`/`zoom`/`front` 三个 role，没写中文 label，所以显示英文；
  - 没有“帮助”菜单；
  - “Web 访问…”和“打开错误日志文件夹”放在“显示”菜单下，位置不合逻辑；
  - 应用菜单没有“偏好设置…（⌘,）”入口；
  - “重新载入窗口”的 ⌘⇧R 属于开发者功能，暴露在普通菜单里。

  方案：随 GUI-01 一起重建菜单：给 role 写中文 label；新增“帮助”菜单，收纳错误日志、使用说明、检查更新；“Web 访问”移到应用菜单或“文件 › 共享”。
- **P5-06（Bug，低，推测待验证）** 剪贴板粘贴网址导入图片时，名称取 `path.basename(new URL(url).pathname)`（`main.js:1417`）：既没有做 URL 解码，也保留了扩展名。中文文件名的图片会以 `%E5%9B%BE.png` 这样的名称入库。方案：先 `decodeURIComponent`，再去掉扩展名（Eagle 的 name 字段不含扩展名）。
- **P5-07（资源，低，源码确认）** 关闭 Web 访问后，即使所有桌面窗口都已关闭，`hub` 的 900ms 轮询也不会停：`applyWebAccess` 不调用 `stopPolling`，`window-all-closed` 只在当时判断一次（`main.js:805-836`、`2467-2471`）。方案：`applyWebAccess` 结束时如果 `windows.size === 0` 且服务未运行，就调用 `hub.stopPolling()`。

### 第二轮 · 本地状态存储与纯逻辑模块（子代理 A3，主会话已抽查核实第 1 条）

范围已全部通读，共 26 个文件：`lib/` 下的 manual-order-store、pin-store、folder-cover-store、supplemental-item-store、text-draft-store、conflict、error-log、app-identity、window-location、window-router、new-file-service、zip-stream、media-mime、preview-image、qr-code；`src/` 下的 sort-memory、pane-state、folder-navigation、eagle-logical-path、smart-folder、operation-state、keyboard-platform、window-actions、window-target、window-router、pane-layout-popover-position。复现脚本只留在云端临时目录，未提交。

- **S-01（安全，中，已复现）`pins:set` 可以污染主进程的 `Object.prototype`。**
  - 位置：`lib/pin-store.js:69-76`；`main.js:2347-2369`；`pins:set` 不在 `HOST_ONLY_CHANNELS` 中，Web 端可以调用。
  - 原因：`folderId` 不做校验就执行 `library[folderId] ||= {}`。
  - 后果：传入 `folderId='__proto__'`、`ids=['isDeleted']` 后，主进程里所有对象都会带上 `isDeleted`，所有素材都被判为已删除，直到重启。传 `ids=['password']` 则所有文件夹都被当成加密。与 P5-03（免密模式加 DNS rebinding）组合后风险更高。
  - 方案：
    - store 改用 `Object.create(null)` 或 `Map`；
    - handler 用与 `folder-cover-store` 相同的 `safeId` 规则校验 `folderId` 和 `ids`，并确认文件夹存在；

- **S-02（Bug，中，已复现）状态文件损坏后，相关功能永久失效。** manual-order、folder-cover、pin、supplemental 四个 store：
  - 写入时只做“临时文件 + rename”，不做 fsync，断电后可能留下空文件；
  - 之后每次 `JSON.parse` 都失败，手动排序、封面、置顶、补充素材持续报错，直到用户手动删除文件；
  - 遇到未知 `version` 时处理不一致：前两个 store 报错，后两个静默当成空数据，下次写入时把原文件覆盖掉。

  方案：抽一个共用的 JSON 状态 store。解析失败时把原文件改名为 `.corrupt-时间戳`，从空状态继续，并写入错误日志。遇到未知版本时只读、拒绝写入。写入临时文件后做 fsync。
- **S-03（性能，中，已复现）每打开一次 TXT 预览，就在磁盘上留下一个草稿墓碑文件，永不清理。**
  - 位置：`lib/text-draft-store.js:82-91`；`src/renderer.js:4338`、`4369-4370`、`4570-4589`。
  - 原因：打开时没有草稿，就生成一个新的 draftId（`renew`），会话是干净的，于是调用 `remove`；而 `remove` 在原本没有记录时也会写墓碑。
  - 后果：草稿目录无限增长，`list()` 每次都对整个目录做 `readdir`，用得越久打开 TXT 越慢。
  - 方案：没有记录时 `remove` 不写墓碑；草稿和墓碑都加 TTL，启动时清理。
  - **已修复（本机会话，2026-10-14，与 S-16 一起）**：从未写过的草稿以 revision 0 删除时不写墓碑；墓碑 24 小时后在首次使用时清理。未保存的草稿正文**不按时间清理**（避免丢文字）。

- **S-05（Bug，中，源码确认）“另存为智能文件夹”在两种视图下的结果比当前视图窄。**

  位置：`src/smart-folder.js:50-51`，对照 `src/renderer.js:2767-2781`。

### 第二轮 · Eagle 注入脚本、TXT 插件、导入与元数据（子代理 A4，主会话已抽查核实 E-01、E-02）

总体结论：
- 注入脚本的所有参数都经过 `JSON.stringify`，不存在拼接注入。
- 每个脚本都会先核对 `libraryPath`，排序、置顶、封面会先比对修改前的原值。
- TXT 写回只调用官方插件 API，路径经 realpath 限定在 `images/<id>.info/` 和暂存目录内。

主要问题如下：

- **E-01（性能，高，已复现）改任何素材的元数据，都会整份读取它的原文件。** `publishItemMutation` 对每个修改过的素材调用 `metadataSearchIndex.refreshItem`（`lib/data-hub.js:416`），而 `refreshItem` 不检查扩展名，直接 `readMetadata` 整份读文件，并且并发不设上限（`lib/metadata-search-index.js:165-188`、`lib/metadata-reader.js:254`）。对比之下，`build` 只处理 png/jpg/webp（`:231`）。给 300 个视频批量打标签，就会同时整份读取 300 个视频文件；超过 2GB 的直接失败；PNG 还会再各启动一个 magick 解码进程。
  - 方案：与 `build` 使用同一份扩展名白名单，并加文件大小上限；放进并发 2～4 的队列；只改标签、名称时只重算文本部分，文件 size/mtime 变化时才重新读文件。
- **E-02（安全／健壮性，中高，已复现）一张特制的 PNG 就能卡死主进程（解压炸弹）。**
  - zTXt/iTXt 解压用的是 `zlib.inflateSync`，没有设 `maxOutputLength`（`lib/metadata-reader.js:27`、`42`）。一张 305KB 的 PNG 让主进程同步阻塞 3.4 秒，内存增加约 600MB。
  - A5 另外复现：parameters 拆分用的正则 `/,\s*(?=[A-Z][^:]+:)/`（`:67`）耗时随长度平方增长，80KB 的文本需要 2.6 秒，几百 KB 就是分钟级。
  - 后台索引会扫描全库，库里只要有一张这样的网图，所有窗口和 Web 服务都会卡住，用户甚至不需要点开它。
  - 方案：
    - 解压设上限 4MB，文本块超过 1MB 直接跳过；
    - 参数拆分改为线性算法；
    - PNG 读到第一个 IDAT 就停止；
    - 解析放到 worker 或 utilityProcess 中执行。
- **E-03（性能，中，源码确认）元数据索引首次构建会读取每一张原图，每张 PNG/WebP 都启动一个 ImageMagick 全量解码，而且没有超时**（`lib/metadata-reader.js:254`、`lib/metadata-search-index.js:236`、`lib/stealth-metadata-reader.js:97-122`）。magick 一旦挂住，这个 worker 就永远卡住，索引永远建不完。另外 ImageMagick 会把文件名里的 `[n]`、`*` 当成帧选择或通配符。
  - 方案：只读文件头部；隐写解码改为检查器里按需执行；子进程加超时。
- **E-04（性能，中，源码确认）每次资料库变更，都会对全库的 `metadata.json` 做一次重复检测扫描，再通过 API 全量拉取一次。**（`main.js:879-898`；`lib/data-hub.js:140`；`lib/duplicate-service.js:120-128`）MultiView 自己设置置顶、调整排序、新建文件夹也会触发。
  - 方案：只有切换资料库时才全量重建，其余情况按事件携带的 id 增量更新。
- **E-05（Bug，中，源码确认）切换资料库后约 2 秒内，旧库的刷新定时器会把搜索索引切回旧库。** 之后在新库里搜索，返回的是旧库的素材 ID（`lib/metadata-search-index.js:127-163`），而 `data-hub` 的 `canUseMetadataIndex` 没有比对索引所属的资料库（`lib/data-hub.js:319-327`）。另外，保存索引时所有写入共用同一个临时文件名，可能互相覆盖。
- **E-06（数据安全，中，已复现）剪贴板里的路径文本会被当成文件导入；如果是目录，会递归导入。** `clipboard.readText()` 读到的绝对路径也被当成文件（`lib/clipboard-files.js:109`、`main.js:1400`）。用户从终端复制一段 `/Users/xx/Downloads` 再按 ⌘V，可能导入其中 2000 个文件。CLAUDE.md 要求“导入只作用于用户明确选择的文件”。
  - 方案：纯文本只接受单个已存在的普通文件；目录只接受来自 Finder 复制的类型，并先确认将导入的数量。

### 附：构建配置（主会话补看 `package.json`）

- **B5-01（安全，低，源码确认）没有配置 Electron fuses**：`RunAsNode`、`EnableNodeCliInspectArguments`、`EnableNodeOptionsEnvironmentVariable` 都保持默认开启，`EnableEmbeddedAsarIntegrityValidation` 没有开。用的是 ad-hoc 签名（`"identity": "-"`），又没有 hardened runtime，本机任意进程都能用 `ELECTRON_RUN_AS_NODE` 或 `--inspect` 借这个应用的身份运行代码；替换 asar 也不会被发现。建议用 electron-builder 的 `electronFuses` 关闭前三项，打开 asar 完整性校验。改完后，需要在本机确认打包、启动和自动更新的 `codesign --verify` 都正常。
- **B5-02（工程，低）`npm test` 是 `node --test`，没有 `--test-force-exit`**，和 CLAUDE.md 写的命令不一致。探针残留的句柄可能让测试进程挂住不退出。建议补上这个参数。**已修复（2026-10-15）**：`test` 脚本改为 `node --test --test-force-exit`。
- 只出 arm64 一种架构（`--arm64`），Intel Mac 不支持。这是已知取舍，记录在此备查。
